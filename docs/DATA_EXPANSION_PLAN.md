# 과거 데이터 확장 계획 (Historical Data Expansion Plan)

> 2026-11-11 작성. **계획 문서이며 아직 대량 수집은 실행하지 않았다.**

## 1. 확인된 사실 (가정 아님)

`tradingos data-range` (이진 탐색으로 OKX `history-candles`를 직접 조회, 타임프레임당 요청 17–23회)로 확인:

| 타임프레임 | OKX가 제공하는 가장 오래된 캔들 (UTC) | 제공 기간 | 전체 봉 수 (추정) |
|---|---|---|---|
| 5m | 2019-12-16 06:05 | 약 2,522일 (6.9년) | 약 726,000 |
| 15m | 2019-12-16 06:00 | 약 2,522일 | 약 242,000 |
| 4H | 2019-12-16 04:00 | 약 2,522일 | 약 15,100 |

- 가장 오래된 지점 직후의 100봉은 연속(결측 없음)이었다.
- **확인하지 못한 것:** 6.9년 전체의 중간 결측 여부. 이진 탐색은 시작점만 알려준다. 수집 후 §4 검증으로만 알 수 있다.
- 상장 초기(2019–2020) 구간은 거래량이 적어 가격 품질(넓은 스프레드, 긴 꼬리)이 다를 수 있다 → 연구 구간에 포함할지는 별도 판단.

현재 저장 상태 (`tradingos data-check`): 5m 51,840봉(180일), 15m 17,280봉(180일), 1H 8,760봉, 4H 4,380봉 — 모두 결측 0, 무결성 OK.

## 2. 수집 방식 (이미 구현된 것)

| 요구 | 구현 | 위치 |
|---|---|---|
| 증분 수집 | 저장 범위보다 과거/최신 구간과 내부 결측 구간만 요청 | `collector.sync_history` |
| 중복 제거 | `ts` 기준, 새 값 우선, 원자적 파일 교체 | `store.merge_save` |
| 누락 구간 검증 | 결측 구간 목록·개수 보고. **채우지 않음** | `validation.validate_candles` |
| UTC 정규화 | `ts` = 봉 시작 시각, UTC epoch ms 정수. 타임프레임 배수 정렬 검사 | `validation` (misaligned) |
| 미완성 캔들 | `confirm=0` 폐기 | `okx_public.parse_candles` |
| 지문 | OHLC 값의 SHA-256 (`data_fingerprint`), 실행 기록에 저장 | `store.data_fingerprint` |
| 4H/15m/5m 정합성 | 5m로 만든 15m·4H와 OKX 원본 비교 (현재 가격 차이 0) | `collector.check_mtf_consistency`, `tradingos data-check` |

요청량: 5m 전체 ≈ 7,300회 요청 × 0.12초 ≈ **15–25분** (재시도 포함). 15m ≈ 2,400회, 4H ≈ 150회. OKX 한도(20회/2초) 이내.

## 3. 실행 단계 (제안)

1. **단계적 확장** — 한 번에 6.9년이 아니라 `--days 730` → 검증 → `--days 1460` → 검증 → 전체. 각 단계 후 `tradingos data-check`.
   ```bash
   tradingos collect --tf 5m  --days 730
   tradingos collect --tf 15m --days 730     # 정합성 비교용 (전략은 5m만 사용)
   tradingos collect --tf 4H  --days 730
   tradingos data-check
   ```
   주의: API의 `MAX_COLLECT_DAYS`는 730이다. 그 이상은 CLI로 수집한다 (UI 한도 상향은 별도 결정).
2. **결측 보고서** — 결측이 나오면 구간·길이를 문서화한다. 전략 쪽 처리는 이미 정의되어 있다: 결측을 포함한 15m/4H 버킷은 폐기, 결측을 가로지르는 스윙·FVG 불성립, 결측 직후 진입 거부(`stale_signal_data_gap`).
3. **정합성 확인** — 5m→15m, 5m→4H, 15m→4H 가격 차이 0 확인. 차이가 나면 해당 구간을 재수집하고 원인을 기록.
4. **데이터 버전 고정** — 연구에 쓸 구간이 정해지면 지문을 기록하고, 이후 실험은 같은 지문에서만 비교한다.

## 4. 아직 구현되지 않은 것 (이번 계획의 구현 항목)

| 항목 | 내용 |
|---|---|
| 출처 메타데이터 | Parquet 옆에 `<bar>.meta.json`: 출처(거래소·엔드포인트), 수집 시각, 요청 범위, 행 수, 지문, 결측 목록, 수집기 코드 리비전 |
| 데이터 버전 | 지문 + 범위를 "데이터셋 버전"으로 명명해 실행 기록이 이름으로 참조 |
| 수정 감지 | 재수집 시 기존 값과 다른 캔들이 있으면 조용히 덮어쓰지 않고 보고 (거래소가 과거 값을 바꾼 경우) |
| 실제 펀딩 요율 | `funding-rate-history` 수집 (제공 범위도 같은 방식으로 먼저 확인) |
| 저장 구조 | 5m 72만 행은 단일 Parquet으로 충분 (수십 MB). 1m까지 확장하면 연도별 분할 검토 |

## 5. 연구 무결성과의 관계

- 데이터를 늘리는 이유는 **표본 수**다. 현재 150일에 ICT 신호 4개로는 어떤 결론도 낼 수 없다. 같은 빈도라면 6.9년에 약 60–70개가 예상되지만, 이는 추정이며 시장 국면에 따라 달라진다.
- 확장한 데이터는 **IS(표본 내)/OOS(표본 외)로 미리 나눈다.** 제안: 가장 최근 20–30%를 OOS로 봉인하고, 정의·파라미터 비교는 IS에서만 한다. 나누기 전에 전체 구간 결과를 보지 않는다.
- 파라미터를 바꿔 본 횟수(시도 수)를 기록한다. 현재 구조: 설정 버전은 불변이고 실행 기록에 설정 해시·데이터 지문·코드 리비전·Inspector 집계가 남는다.
