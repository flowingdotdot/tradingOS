# Trading OS — 리스크 정책 (Risk Policy)

> 상태: v0.1. 아래 수치는 **잠정 한도(provisional limits)** 이며 최적값으로 검증된 것이 아니다.
> 원칙: **확실하지 않으면 거래하지 않는다 (When in doubt, stay out).**

## 1. 거래 리스크 한도 (DEMO 초기값, 백테스트 기본값)

| 항목 | 값 | 적용 위치 |
|---|---|---|
| 거래당 리스크 | 계좌 자산의 **0.25%** | RiskEngine.size_position [구현됨] |
| 일일 손실 한도 | **1%** (UTC 자정 기준 시작 자산 대비, 실현손익+비용) | RiskEngine.can_open [구현됨] |
| 동시 포지션 | **1** | RiskEngine.can_open [구현됨] |
| 최대 레버리지 (명목/자산) | **3x** (사이징 결과가 넘으면 수량 축소) | RiskEngine.size_position [구현됨] |
| 마틴게일 / 물타기 | **금지** | 엔진 구조상 포지션 보유 중 추가 진입 불가 [구현됨] |
| 자동 레버리지 상향 | **금지** | 설정 외 경로 없음 |

### 용어 설명
- **거래당 리스크 0.25%**: 손절에 걸렸을 때 잃는 금액이 자산의 0.25%가 되도록 수량을 정한다.
  예) 자산 10,000 USDT, 진입 70,000, 손절 70,700 (숏) → 손절폭 700 USDT/BTC → 수량 = 25 / 700 = 0.0357 BTC → 계약 단위(0.0001 BTC = 0.01계약×0.01) 내림.
  **2026-11-12부터 수량은 비용을 포함해 계산한다**: `수량 = 위험 예산 / (손절 손실 + 진입·청산 수수료 + 손절 슬리피지)`,
  계약 단위로 내림, 최소 주문 미달 시 거부 ([BACKTEST_EXECUTION_MODEL.md](BACKTEST_EXECUTION_MODEL.md) §6).
  따라서 정상 손절의 손실은 약 0.25%다. 손절가를 갭으로 넘는 경우와 펀딩은 포함되지 않아 그보다 클 수 있다.
- **레버리지 vs 리스크**: 레버리지는 리스크를 정하지 않는다. 리스크는 *수량 × 손절폭*이 정한다. 레버리지 한도는 손절폭이 매우 좁을 때 명목가치가 과도해지는 것을 막는 2차 안전장치다.
- **일일 손실 한도**: 도달 시 그날(UTC) 남은 시간 동안 **신규 진입 차단**. 보유 포지션은 자체 손절/목표로 정상 관리.

## 2. 주문 승인 규칙 (Order Authorization) — 모든 신규 진입에 적용

신규 진입은 다음을 **모두** 만족해야 한다. 하나라도 실패하면 거부하고 사유를 기록한다.

1. 실행 환경이 허용됨 (LIVE는 항상 거부 — §7)
2. 시스템 상태가 `HEALTHY` (Phase 4: 데이터 신선도, 연결, 대사 완료)
3. 손절가 존재, 진입가 기준 **올바른 방향** (롱: stop < entry, 숏: stop > entry), 손절폭 > 0
4. 계산 수량 ≥ 거래소 최소 수량 (`minSz`), 계약 단위로 내림
5. 레버리지 한도 내 (초과 시 축소, 축소 후 최소 수량 미달이면 거부)
6. 동시 포지션 한도 미만
7. 일일 손실 한도 미도달
8. [Phase 4] 사용 가능 증거금 충분

## 3. 데이터 무결성 규칙
- 미완성 캔들(`confirm=0`)로는 어떤 의사결정도 하지 않는다.
- [Phase 4] 마지막 확정 캔들이 `봉길이 + 30초`보다 오래되면 **stale** → 신규 진입 차단.
- 결측 구간(gap)은 채워 넣지 않는다 (가짜 캔들 생성 금지). 백테스트 결과에 결측 정보를 표시한다.

## 4. 실행 안전 규칙 (Phase 4 구현 대상)
- 모든 주문에 고유 `clOrdId` (전략·신호·시도 기반 결정적 ID) → **중복 주문 방지**.
- 응답이 불명확한(타임아웃 등) 주문 제출은 **절대 맹목적으로 재시도하지 않는다**: 먼저 `clOrdId`로 주문 조회 → 존재하면 그 상태를 따르고, 없음이 확인될 때만 재제출.
- 부분 체결: 체결된 수량 기준으로 손절 주문 수량을 맞추고, 미체결 잔량은 정책에 따라 취소.
- 진입 후 **거래소 측 보호 손절(attached SL/algo order)** 존재를 조회로 확인. 일정 시간 내 확인 실패 시 포지션 즉시 시장가 청산 + 경보.
- 재시작 시: 거래소 포지션·미체결 주문 조회 → 로컬 저널과 대사 → 불일치(예: 모르는 포지션) 시 `UNCERTAIN` 상태로 신규 진입 차단, 사람의 확인 요구. 모르는 포지션은 자동으로 건드리지 않되, 보호 손절이 없으면 경보.
- 증거금 부족 오류: 재시도하지 않고 거부로 기록.
- WebSocket 단절: 재연결 + REST로 누락 캔들 보충 + 대사 완료 전 신규 진입 차단.

## 5. 비상 제어 (Kill Switch) — Phase 4
- **진입 정지(Halt entries)**: 신규 진입만 차단.
- **전량 청산(Flatten)**: 모든 미체결 주문 취소 → 모든 포지션 시장가 청산 → 진입 정지 상태 유지.
- 킬스위치 상태는 영속화되어 재시작 후에도 유지되며, 해제는 수동으로만.

## 6. 자격증명 보안
- API 키/시크릿/패스프레이즈는 **환경변수 또는 OS 비밀저장소에서만** 읽는다. 코드·YAML·git·로그·프론트엔드에 절대 노출 금지.
- 로깅 필터가 알려진 비밀 필드명(`api_key`, `secret`, `passphrase`, `OK-ACCESS-*` 헤더 등)을 마스킹한다 [구현됨].
- API 키 권한: **읽기 + 거래만**. **출금(Withdraw) 권한 절대 금지.** 가능하면 **IP 제한** 설정.
- DEMO 키와 LIVE 키는 별도 변수 이름(`OKX_DEMO_*` / `OKX_LIVE_*`). 현재 코드는 `OKX_LIVE_*` 를 읽지 않는다.
- API 응답에 자격증명 값을 포함하지 않는다. UI는 "설정됨/미설정" 여부만 표시.

## 7. LIVE 활성화 절차 (현재: 불가)
LIVE는 배포 설정으로 켜지는 모드가 아니다. 다음이 모두 충족된 뒤 **별도 코드 변경 PR**로만 도입한다:
1. 전략이 `DEMO_FORWARD_TESTED` 단계에서 사전에 정한 기간/거래 수 기준을 충족 (사람의 리뷰)
2. Phase 6 실행 신뢰성 테스트(장애 주입, 재시작, 부분 체결, 단절) 통과
3. 보안 감사 (키 권한, 로그, 비밀 저장)
4. 운영 준비도 체크리스트 (모니터링, 알림, 비상 절차 훈련)
5. 매 실행 시 명시적 수동 확인 + 축소된 리스크 한도로 시작

## 8. 면책
백테스트·DEMO 결과는 가상의 성과이며 미래 수익을 보장하지 않는다. 시스템은 어떤 결과도 "수익 보장"으로 표시하지 않는다.
